Case study 01 · Loyalty & retail · Payments

Many payment gateways, one clean interface

Sure Benefits is a loyalty app where members earn and redeem points with QR codes at partner merchants. People pay in different ways, so the app had to support several payment gateways without turning the checkout code into a tangle.

01 / The setup

Points, QR codes and real money in one app

Members collect points, see special benefits and redeem them by scanning a QR code at a merchant. The app works with 50+ merchants, and some actions involve paying through one of several payment gateways.

The app is built in Flutter with GetX for state and dependency management.

02 / The problem

Every gateway worked differently

Each gateway had its own way to start a payment, its own screens and its own success and error responses. Calling each one directly from the checkout screen would have spread gateway-specific code across the UI.

That makes every new gateway risky: a change for one provider could break checkout for the others, and testing the checkout meant testing every provider at once.

03 / The fix

One payment interface, an adapter per gateway

I put all gateways behind a single PaymentService interface. The UI only knows that interface.

01

One interface for the UI

The checkout calls the same methods for every gateway and receives the same result type, so the screen code stays small.

02

One class per gateway

Each provider's details live in its own implementation. A bug in one gateway stays inside that class.

03

Swap with dependency injection

GetX provides the right implementation for the method the user picks, so the screen doesn't switch on gateway names.

04

Adding a gateway is additive

Supporting a new provider means writing one new class, without touching the checkout screen.

// Simplified: the UI only knows this interface.
abstract class PaymentService {
  Future<PaymentResult> pay(PaymentRequest request);
}

class GatewayAPayment implements PaymentService { /* provider A details */ }
class GatewayBPayment implements PaymentService { /* provider B details */ }

// Checkout: same call whichever gateway the user chose
final result = await Get.find<PaymentService>(tag: method).pay(request);
04 / The result

Checkout stayed simple as the app grew

The checkout screen stayed the same size no matter how many gateways were added, and each gateway could be fixed or tested on its own. Alongside QR redemption and merchant tools, the app supported a loyalty program across 50+ merchants.

What I took from it: when a feature has many providers, the best thing to design is the seam between them and the UI. A small interface made the rest of the work routine.
