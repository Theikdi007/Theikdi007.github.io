Making doctor–patient chat reliable in Careme

Careme connects patients with doctors and nurses in Myanmar. Chat is where care happens between visits, so a lost, doubled or misordered message is not a small bug. This is how I built the chat and fixed the reconnect problems that made it feel unreliable.

Role
Senior Flutter Developer
Apps
Patient · Doctor · Nurse
Scale
5,000+ monthly users
01 / The setup

Three Flutter apps, one real-time backend

Careme has separate apps for patients, doctors and nurses, all built in Flutter. They share an ASP.NET Core backend with SQL Server. Live messages travel over a SignalR hub, and Firebase Cloud Messaging reaches users whose app is closed or in the background.

On the phone, state lives in GetX controllers and services. Every chat is cached locally, so a conversation opens instantly and still shows its history without a connection.

02 / The problem

After a reconnect, messages showed up twice or out of order

Mobile networks in Myanmar drop often, and phones put apps to sleep. Every time the app came back, three things happened close together: SignalR reconnected, the app loaded missed history over REST, and FCM pushes arrived for the same messages.

Each of these paths added messages to the screen in the order they arrived, not the order they were sent. On top of that, reconnecting registered a fresh set of SignalR listeners without removing the old ones, so one incoming message could fire the handler twice. For a patient reading a doctor's instructions, a duplicated or shuffled thread looks broken and is hard to trust.

03 / The fix

One source of truth, keyed by message ID

I treated every way a message can arrive as an input to the same merge step, instead of letting each path write to the UI directly.

01

A single SignalR connection

The connection lives in one long-lived GetX service. Handlers are registered once and cleaned up before a reconnect, so one message fires one event.

02

Unique message IDs

Every message carries an ID. The controller skips any ID it already holds, whether the copy came from SignalR, REST or a push.

03

Order by the server, not by arrival

The list is sorted by the server's timestamp and sequence, so a message that arrives late still lands in its correct place.

04

Merge history into the cache by ID

On reconnect, history from the API is upserted into the local cache by ID. The cache is the one list the UI reads from.

// Simplified: every path (SignalR, REST history, push) ends here.
void upsertMessages(List<ChatMessage> incoming) {
  for (final m in incoming) {
    _byId[m.id] = m;          // same ID = same message, no duplicate
  }
  messages.value = _byId.values.toList()
    ..sort((a, b) => a.serverSeq.compareTo(b.serverSeq));   // server order
  _cache.putAll(incoming);    // local cache keyed by ID
}
04 / The result

Chat that holds up on real networks

Conversations now open instantly from the cache, catch up on their own after the network returns, and show each message once, in the order it was sent. The same pattern carries across the patient, doctor and nurse apps.

What I took from it: in real-time apps, the hard part is rarely sending a message. It is agreeing on one true list when the same data can arrive from several directions. Making the client idempotent by ID turned a class of flaky bugs into a single, testable function.
